# 작업 지시: DCSS_SV 3단계 마무리와 그 뒤

> **지난 기록.** 3단계(`stage3-wip`) 시절의 인수인계 문서다. 여기의 상태와 할 일은 끝났다. 2절의 규칙 중 유효한 것은 [DEVELOPMENT_GUARDRAILS.md](DEVELOPMENT_GUARDRAILS.md) §6으로 옮겼다. 문서 목록은 [README.md](README.md).

너는 이 저장소(`jinha1226/DCSS_SV`)의 개발을 이어받는다. 앞사람이 0~2단계를 끝내 main에 올렸고, 3단계를 만들던 중에 넘긴다. 이 문서를 끝까지 읽고 시작해라. 모르는 것은 추측하지 말고 코드와 `docs/PLAN.md`를 먼저 읽어라.

## 1. 무엇을 만드는가

DCSS(Dungeon Crawl Stone Soup)식 던전에서 떼를 상대하는 **실시간 2D 뱀서류**다. 종족과 직업을 고르고, 층을 내려가며, 레벨업마다 스킬 카드를 하나 고른다. 공격은 자동이고 조작은 이동과 버튼 몇 개다.

- 해 보는 곳: <https://jinha1226.github.io/DCSS_SV/> (main에 올리면 GitHub Actions가 배포한다)
- 사용자는 **폰을 세로로 들고** 이 링크로만 시험한다. PC와 가로 화면은 지금 못 본다.
- 먼저 읽을 것: `docs/PLAN.md`(단계별 계획과 지금까지 정한 것), `docs/TILES.md`(타일 출처와 라이선스), `README.md`.

지금 만드는 것은 **첫 시험판**이다: 미노타우로스 광전사 하나, 층 셋, 오 분. 답할 질문은 "던전 안에서 떼를 상대하며 커 가는 기본 판이 손에 붙는가" 하나다.

## 2. 어기면 안 되는 것

1. **DCSS에서는 타일만 가져온다.** DCSS의 코드, 볼트 파일, 설명문은 열어 보고 옮기지 않는다(GPL). 수치와 생성 방식은 새로 짠다.
2. **타일을 더할 때마다 라이선스를 대조한다.** <https://github.com/crawl/tiles> 의 `TILES_UNDER_UNKNOWN_LICENSE.md`에 있는 이름은 쓰지 않는다. 예: `javelin` 계열은 전부 그 목록에 있어서 못 쓴다. 더한 타일은 `docs/TILES.md` 표에 적고 `npm run tiles`를 돌린다. `assets/tiles`에는 DCSS 원본 PNG만 둔다.
3. **구조를 지킨다.** `src/sim`은 규칙이고 DOM과 캔버스를 모른다(테스트와 봇이 여기만 쓴다). 수치는 `src/data`의 표에 둔다. 그리기는 `src/view`, 입력은 `src/input`, 화면 위 글자와 버튼은 `src/ui`, 시작점은 `src/app`. 파일 하나는 500줄까지(ESLint가 막는다). 한 파일에 몰아 쓰거나 줄을 압축하지 마라.
4. **코드를 한 줄에 몰아 쓰지 않는다.** 올리기 전에 `npm run format`(Prettier)을 돌린다. `npm run lint`가 모양까지 검사하므로, 돌리지 않으면 배포가 막힌다. 문장 하나에 한 줄, 한 줄은 140자까지. 4·5단계에서 한 줄에 수백 자씩 몰아 쓴 코드가 들어와 전부 다시 풀어야 했다. 형식 검사를 끄거나 `.prettierignore`에 소스를 넣어 피하지 마라.
4-1. **`npm run check`(린트, tsc, 테스트)와 `npx vite build`가 통과해야 올린다.** tsconfig는 strict에 `noUncheckedIndexedAccess`다. 규칙을 바꾸면 테스트를 같이 바꾸거나 더한다.
5. **한 번에 커밋 하나로 올린다.** 파일마다 커밋을 나눠 연달아 push하면 배포 작업이 서로를 취소해서 최신 커밋이 안 돈다. push 뒤에 Actions가 성공했는지 확인한다.
6. **눈이 피로한 효과를 넣지 않는다.** 화면 전체가 번쩍이거나 흔들리는 것, 가산 합성(밝게 겹치는 빛)은 금지다. 맞은 적만 잠깐 밝아지고 숫자가 뜬다. 사용자가 이전 프로젝트에서 이 때문에 여러 번 불편을 말했다.
7. **페이지 확대를 막아 둔 것을 깨지 않는다**(`src/input/guards.ts`, `index.html`의 viewport, CSS `touch-action`). 새 버튼을 만들어도 더블탭과 두 손가락 확대가 일어나면 안 된다.
8. **사용자가 브레인스토밍으로 한 말을 바로 만들지 않는다.** "~하면 어떨까"는 의견을 묻는 것이다. 만들라고 할 때 만든다. 단계 하나가 끝나면 폰에서 볼 것을 알려 주고 한 줄 느낌을 들은 뒤 다음 단계로 간다.
9. `npm run bench`(봇 측정)는 배포 작업에 넣지 않는다. 느리다. 기준은 `tests/unit`의 빠른 테스트로 남긴다.
10. 사용자에게는 **편한 한국어**로 답한다. 결론부터, 짧게. 확인하지 못한 것(실제 폰의 느낌)은 확인 못 했다고 말한다.

## 4. 사용자가 정한 것 (바꾸지 마라)

- 바닥과 벽은 **원본 1층 타일**(grey_dirt, brick_brown).
- 한 화면 가로 **17칸**, 걷는 속도 **1초에 6.5칸**.
- **복도는 한 칸 폭이어도 된다.** 대신 **한 칸에 몬스터 둘이 겹쳐 서면 안 된다.** 그래서 몬스터 반지름을 0.38~0.48로 키웠다. 화면에서 스프라이트가 포개져 보이면 이 결정을 어긴 것이다.
- **던지는 무기는 근접 캐릭터에게 필수다. 마법처럼 버튼으로 쓰고, 원거리 몬스터를 가장 먼저 노린다.** 규칙은 들어 있다(`throwTarget`: 던지는 몬스터 → 깨어 있는 몬스터 → 자는 몬스터 순, 각각 가장 가까운 것). 버튼이 없다. 지금은 탄약 없이 1.4초 재사용이고 부메랑 타일을 쓴다. 탄약을 둘지는 5단계(장비)에서 사용자에게 묻는다.
- 걷는 모습은 서 있는 타일을 잘라 코드로 만든다(`src/view/walk.ts`). 그림 파일을 따로 그리지 않는다.
- 2단계에서 정한 싸움의 뼈대: 몬스터는 치기 전에 젖히고 그 사이 벗어나면 빗나간다. 도끼는 살짝만 밀고 크게 미는 것은 뿔 받기다. 몬스터는 플레이어를 막는다. 체력은 천천히 저절로 찬다.

## 5. 할 일 ① 3단계 마무리 (`stage3-wip`에서)

**화면** (전부 `src/view`, `src/ui`, `src/input`, `src/app`. 규칙은 건드릴 필요가 거의 없다)

1. tsc 오류 2개와 실패 테스트 1개를 먼저 고친다.
2. **날아가는 것 그리기**: `w.shots`. `mine`이 false면 돌(`item/stone`), true면 부메랑(`item/boomerang1`, 날아가는 동안 돈다). `px`, `py`로 걸음 사이를 이어 그린다. 타일 반 크기쯤.
3. **던지기 버튼**: 오른쪽 아래에 엄지로 누를 둥근 버튼(DOM, 최소 64px). 누르면 다음 걸음의 `Input.throw`가 true다. 재사용 대기(`hero.throwing` / `HERO.thrown.every`)가 보이게 한다. 버튼 위의 터치가 스틱을 시작하면 안 되고, 스틱을 쥔 채로 다른 손가락으로 누를 수 있어야 한다. PC는 스페이스와 `KeyJ`(`src/input/keys.ts`처럼 `e.code`로 읽는다).
4. **노리는 대상 표시**: `throwTarget(w)`가 고른 몬스터에 가는 고리를 그린다. 누르면 누가 맞을지 보이게.
5. **자는 몬스터 표시**: `awake`가 false면 머리 위에 작은 `z`.
6. **계단**: 내려가는 계단에 서 있으면 `w.descending / DUNGEON.descend`만큼 고리가 차오른다.
7. **화면 위 정보**(`src/ui/hud.ts`): 층(`1/3층`), 독에 걸리면 체력 막대 색을 바꾼다, 탈출하면 끝 화면 제목이 "던전을 빠져나왔다". `floor` 이벤트가 오면 `fx.clear()`.
8. **작은 지도**: 오른쪽 위에 가 본 칸(`w.seen`), 계단, 내 위치를 그린다. 48×48칸을 칸당 2px쯤으로. 계단을 찾아 내려갈지 더 뒤질지를 정하려면 필요하다. 터치를 받지 않게 한다.
9. 몬스터 체력 막대는 `m.maxHp` 기준으로(깊은 층은 체력이 더 많다). 오우거처럼 오래 젖히는 몬스터는 젖히는 동작이 더 크게 보이게.
10. 주소 스위치 `?floor=2`(시작 층)를 `src/app/switches.ts`에 더하고 테스트도 더한다.

**재기** (`tests/bench`)

11. `tests/bench/bots.ts`의 `play`가 새 `makeWorld({ seed })`를 쓰게 돼 있다. 여기에 **탐험하는 봇**을 더한다: 깨어 있는 적이 가까우면 기존 `dance`처럼 싸우고, 던질 수 있으면 던지고, 없으면 본 적 있는 내려가는 계단으로, 그것도 없으면 가 보지 않은 곳과 맞닿은 칸으로 걷는다(가 본 칸 위에서 BFS). 계단 위에서는 선다.
12. `npm run bench`로 **서른 판**을 돌려 층마다 걸린 시간, 쓰러진 층, 탈출한 판 수를 낸다. 결과를 `docs/PLAN.md`의 3단계에 표로 적는다.
13. 숫자는 `src/data`에서만 맞춘다. 3단계의 목표(레벨업이 아직 없다는 점을 감안해서): 가만히 서 있는 봇은 1층에서 쓰러진다. 탐험하는 봇은 2층까지는 대개 가고 3층에서 자주 쓰러진다. 한 층에 60~120초. 탈출이 열 판 중 한두 판을 넘으면 너무 쉬운 것이다. 2단계에서는 가만히 선 봇이 평균 65초, 잘 움직이는 봇이 164초를 버텼다.
14. 3단계의 기준을 테스트로 남긴다(`tests/unit/balance.test.ts`를 새로: 가만히 선 봇은 쓰러진다, 탐험하는 봇이 더 깊이 간다). 느리면 판 수를 줄인다.

**문서와 올리기**

15. `docs/PLAN.md`: 2단계 체크, 4절의 결정들을 "2단계에서 정한 것"으로 적는다. 계획서에 "두세 칸 폭 통로"라고 적힌 곳을 고친다. 투척이 자동에서 버튼으로 바뀐 것을 4단계 스킬 표에도 반영한다(투척 스킬은 피해, 재사용 시간, 한 번에 던지는 수를 올린다).
16. `README.md`의 주소 스위치, `docs/TILES.md`.
17. 폰 크기(390×844, 터치)로 띄워 직접 본다. 스틱과 던지기 버튼을 같이 쓸 수 있는지, 떼가 겹쳐 보이지 않는지, 한 칸 복도에서 몬스터가 막히지 않는지, 층을 내려가지는지, 3층에서 탈출 화면이 뜨는지.
18. `stage3-wip`을 main에 합쳐(커밋 하나로 정리해도 된다) push하고 Actions 성공을 확인한다.
19. 사용자에게 알린다: 무엇이 들어갔는지, 봇 숫자, **폰에서 볼 것**(통로와 방이 싸우는 법을 바꾸는가, 더 뒤질지 내려갈지가 고민되는가, 던지기 버튼이 손에 맞는가, 몬스터 여덟 종이 서로 다르게 느껴지는가).

## 6. 할 일 ② 그 뒤 단계 (`docs/PLAN.md`를 따른다. 단계마다 사용자 확인을 받고 넘어간다)

**4단계 성장**: 경험치, 레벨업 때 멈추고 스킬 카드 셋 중 하나. 스킬은 도끼, 전투, 갑옷, 방패, 회피, 투척의 여섯, 각 8단계. 매 단계 숫자가 오르고 2·4·6·8단계에는 싸우는 모습이 바뀐다. **만들기 전에 단계별 효과 전체 표를 사용자에게 먼저 보여 주고 확인받는다.** 카드에는 이름, 지금 단계, **쉬운 한 줄**만 적는다(이전 프로젝트에서 "스킬이 안 읽힌다"는 말이 있었다). 방어는 원본처럼 AC(피해 감소), EV(회피), SH(막기) 셋이다. 미노타우로스는 근접과 방어 스킬이 한 번에 더 오른다.

**5단계 장비**: 도끼가 바닥에 떨어진다. 체급 셋(가벼운 한손, 무거운 한손, 양손. 양손이면 방패를 못 든다), 속성 넷(화염, 냉기, 전격, 흡혈), 랜다트(속성 하나에 무작위 옵션 두세 개와 지어낸 이름), 픽다트 둘(숫자가 아니라 규칙을 바꾼다. 예: 불탄 적이 죽으면 터진다). 가방은 없고, 밟으면 멈추고 지금 것과 나란히 보여 준 뒤 바꿀지 버릴지만 고른다. 몬스터의 저항은 원본과 같은 종류(화염, 냉기, 음에너지, 전기, 독). 던지는 무기에 탄약을 둘지 이때 묻는다.

**6단계 다듬기와 측정**: 결과 화면, 봇으로 난이도 맞추기(목표 표는 `docs/PLAN.md`), 폰에서 나온 느낌 반영.

**시험판 다음**(기획에서 정해진 것만 적는다. 시험판의 답이 좋을 때 하나씩): 바라치 궁수(걸음이 느리고 도약이 버튼, 시야가 넓다) → 딥엘프 컨저러 → 바라치 마검사(무기로 공격하고 낮은 레벨의 쓸 만한 주문을 곁들인다. 무기에 속성을 입히는 캐릭터가 아니다) → 밟아서 감정하는 물약과 두루마리 → 칭호와 신 → 지역별 지형과 볼트. 마법은 이렇게 정해져 있다: 학파 단계마다 공격 주문 하나가 생긴다(7레벨까지, 8레벨부터는 마법 신). 기본 공격 주문은 마나 없이 자동으로 나가고 학파가 오르면 한 단계 늦게 따라 올라간다. 그 위의 주문은 마나를 쓰는 버튼이다. 마나는 시간에 따라 찬다. 뱀서의 진화 같은 조합식은 넣지 않는다. 장비는 카드와 별개로 줍는다. 카드는 전부 스킬이다.

## 7. 코드 지도 (main 기준, stage3-wip에서 바뀐 것은 3절)

- `src/app/main.ts` 시작점. `loop.ts` 고정 간격(1/60초) 걸음과 그리기. `switches.ts` 주소 스위치(`?zoom ?speed ?look ?seed ?debug`).
- `src/sim/world.ts` `makeWorld`, `stepWorld`. `types.ts` `World`, `Hero`, `Monster`, `SimEvent`(규칙이 화면에 알리는 일. 규칙은 이것을 다시 읽지 않는다).
- `src/sim/collide.ts` 원과 벽의 충돌(`moveCircle`). `fov.ts` 시야. `flow.ts` 플레이어까지의 거리 지도와 몬스터의 길. `grid.ts`, `rng.ts`.
- `src/view/render.ts` 그리기. `atlas.ts` 타일 시트와 물들인 사본(맞았을 때). `walk.ts` 걷는 모습. `fx.ts` 궤적과 떠오르는 숫자. `look.ts` 바닥과 벽 타일.
- `src/input/stick.ts` 누른 자리에 생기는 스틱. `keys.ts` 키보드. `guards.ts` 확대 막기.
- `src/ui/hud.ts` 체력, 시간, 처치, 끝 화면. `src/styles/main.css`.
- `tools/packTiles.mjs` 타일 묶기. `tests/bench/bots.ts` 봇.
- `?debug`를 붙이면 `window.__sv`로 `world` 등을 볼 수 있다.

## 8. 앞서 실제로 있었던 실수 (되풀이하지 마라)

- 계획의 0단계만 하라는데 "playable prototype"을 한 파일에 압축해 올렸다. 계획에 없는 것을 앞질러 만들지 마라.
- 빈 배열에 타입을 안 줘서 `tsc`가 배포를 막았다. 올리기 전에 `npm run check`를 돌려라.
- 파일마다 커밋을 나눠 올려 배포 작업이 서로를 취소했다.
- 걷는 모습을 엉덩이에서 잘라 허리에 끊긴 줄이 보였다. 그림을 만들면 크게 띄워 눈으로 확인해라.
